## What and why

Sakshi's later modules convert an image to OCR text. This sprint implements
Jigisha's next step: text to a document type. It is simple application logic
built on OCR, rather than a new DIP operation. There is no trained model,
network call, image processing, extraction or readiness calculation here.

Before implementation, case/whitespace normalization, keyword evidence,
conflicting types and the limits of fixed rules were explained in chat.
The expected output is the contract-v1 dictionary:


## How the code works

`modules/classification.py` exports `classify_document(text)`. It requires a
string and creates a normalized copy using `casefold()` and
`" ".join(text.split())`. For example, `INCOME\n  Certificate` becomes
`income certificate`. The caller's original OCR text remains available with
its original formatting; later callers must retain it in their document record.

`TITLE_KEYWORDS` contains the explicit demonstration vocabulary:

| Type ID | Matching phrases |
|---|---|
| `income_certificate` | `income certificate` |
| `caste_certificate` | `caste certificate` |
| `marksheet` | `marksheet`, `mark sheet` |
| `identity_proof` | `identity proof` |

`re.escape(keyword)` treats each phrase literally. The surrounding
`(?<!\w)` and `(?!\w)` checks prevent matching inside longer words, so
`Identity Proofreading` does not match `identity proof`. Punctuation around
a title is accepted; punctuation replacing the space within a title is not.

One matching type returns that type. No matching type returns `unknown`
with empty evidence and `ambiguous=False`. Two or more matching types return
`unknown` with all matching phrases and `ambiguous=True`. Repeating one title
five times does not outvote a conflicting title. Two spellings of the same
type do not create ambiguity. Evidence is a deterministic list of normalized
matched phrases, each listed once, in vocabulary order. It is not a probability.

Non-string input raises a clear `TypeError`; missing OCR/setup errors should be
handled explicitly by callers. No filename argument or filename-based fallback
exists. A new evidence list is created for each call.

The four reference documents use the fictional name `Asha Example`, ID

future extraction expectations; no field extractor is implemented or tested
in JB01. Unknown/ambiguous cases specify no expected extracted fields.

## Limits and next action

This vocabulary fits the agreed demonstration layouts. Generic terms such as
`income` alone are insufficient. Misspelled titles such as
`Inc0me Certiflcate`, translations, unsupported synonyms, unusual punctuation
and unhandled OCR errors can return unknown. No fuzzy matching was added.
An unrelated page mentioning one exact title could be classified as that type;
the rule does not understand document purpose or authenticity. A checklist
mentioning several titles remains conservatively ambiguous. These rules do
not establish whether uploads belong to the same person or meet official rules.

label-aware `extract_fields(text, doc_type)` against the reference fields;

values. Real OCR robustness waits for M01 and subsequent validation. M01 is
